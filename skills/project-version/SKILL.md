# 项目版本维护

根目录 `VERSION` 是唯一版本来源，格式为 `MAJOR.MINOR.PATCH[-rc.N]`。
CMake 从中提取数值部分用于 `project(VERSION)`，保留完整版本用于配置输出。
项目目前处于测试阶段，内部测试版本统一使用 `-rc.N` 后缀，每个新测试基线从 `rc.0` 开始。
当前数值基线为 `1.0.0`，记为 `1.0.0-rc.0`；这不表示已发布过稳定版 1.0.0。

## 每次提交

1. 检查 `git status`、待提交差异、HEAD 中的 `VERSION` 和已有版本标签。
   评估库接口、共享内存/PDO 协议、启动参数及配置格式的兼容性。
2. 优先使用本次指令明确指定的更新类型。未指定时，先说明兼容性判断及建议版本，
   再询问用户“本次是内部测试更新，还是 patch 更新？”；如新增能力或破坏兼容性，
   同时指出应选 minor/major，不能把不兼容变更当作兼容 patch。
3. 更新 `VERSION`，与本次改动放入同一个提交；包括纯文档、配置或 skill 改动。
   同一次提交的准备过程只递增一次，若工作区已含相对 HEAD 的正确版本更新则复用。
   确认暂存区内包含版本更新，完整版本不同于父提交且不与已有发布标签冲突。
4. 验证版本格式，运行与实际改动对应的检查；在提交说明中写明更新类型、
   完整版本和兼容性影响。仅在用户要求提交时创建提交；本 skill 不自动授权发布或打标签。

## 递增规则

- **内部测试**：当前为 `X.Y.Z-rc.N` 时仅递增 N，例如 `1.0.0-rc.0` →
  `1.0.0-rc.1`。同一未发布测试周期内允许调整接口，但要记录迁移影响。
  从稳定版开始新测试周期时，按兼容性选下一个 patch/minor/major 基线并加 `-rc.0`，
  不生成低于已发布稳定版的同基线预发布版本。
- **patch**：兼容修复，递增 PATCH，明确要求测试版本时使用 `-rc.0`；
  例如 `1.0.0-rc.3` → `1.0.1-rc.0`。测试阶段未明确要求稳定发布时保留预发布后缀。
- **minor**：向后兼容的新功能，递增 MINOR、PATCH 归零；测试阶段使用 `-rc.0`。
- **major**：破坏兼容性，递增 MAJOR、MINOR/PATCH 归零；测试阶段使用 `-rc.0`。
- **转稳定版**：只有用户明确要求发布稳定版才去掉后缀，例如 `1.0.1-rc.4` →
  `1.0.1`；不要把“patch 更新”自动理解为稳定发布。

用户明确指定的版本优先；若与已有发布顺序或兼容性判断冲突，说明冲突并确认。
不使用 `+build` 代替版本递增，因为 SemVer 排序不考虑构建元数据。
