# 项目版本维护

根目录 `VERSION` 是唯一版本来源，格式为 `MAJOR.MINOR.PATCH` 或
`MAJOR.MINOR.PATCH-rc.N`，各部分为无前导零的非负整数。
CMake 提取数值部分用于 `project(VERSION)`，保留完整版本用于配置输出。
项目目前处于测试阶段，但内部测试与正式发布必须分别处理；从 `VERSION`、
Git 历史和标签读取实际基线，不在本 skill 中硬编码当前版本。

## 确定更新类型

每次创建 Git 提交都更新 `VERSION`，包括文档、配置和 skill 改动。
先检查工作区、暂存区、HEAD 中的版本及已有 `vX.Y.Z` 标签，评估库接口、
共享内存/PDO 协议、启动参数、配置格式和运行行为的兼容性。
发布时评估自最近相关正式发布以来的累计改动，不能只看最后一次 RC 提交。

- 用户已明确要求内部测试、patch、minor、major 或具体发布版本时，沿用该选择，
  不重复询问。明确的版本号优先于自动递增；明确要求“发布 3.0.1”即使用 `3.0.1`。
- 未明确类型时，先说明兼容性判断和候选版本，再询问
  “本次是内部测试更新，还是 patch 发布？”。有新增功能或破坏兼容性时，
  改为推荐并确认 minor 或 major 发布。可以继续准备改动和检查，
  但须得到选择后才能确定最终版本、提交和打标签。
- “patch 更新”“minor 更新”“major 更新”按正式发布处理，去掉 RC 后缀并打标签；
  只有明确指定内部测试或 RC 时才使用预发布版本。
- 若用户选择与兼容性结论冲突，说明具体迁移影响和建议版本并确认，
  不默默将不兼容改动标为兼容 patch。版本倒退或标签已存在时同样先报告冲突。

## 兼容性与递增规则

| 类型 | 适用改动 | 版本规则 |
| --- | --- | --- |
| 内部测试 | 尚未正式发布的迭代 | `X.Y.Z-rc.N` → `X.Y.Z-rc.(N+1)`，不打正式标签 |
| patch | 向后兼容的修复、文档或维护改动 | `X.Y.Z` → `X.Y.(Z+1)` |
| minor | 向后兼容的新功能 | `X.Y.Z` → `X.(Y+1).0` |
| major | 破坏既有接口、协议、配置或行为兼容性 | `X.Y.Z` → `(X+1).0.0` |

从正式版开始内部测试时，按兼容性选下一个 patch/minor/major 基线并加 `-rc.0`，
例如 `3.0.1` 的兼容修复进入 `3.0.2-rc.0`，不能退回 `3.0.1-rc.0`。
同一未发布 RC 周期通常只递增 N；若累计改动要求比既定发布基线更高的升级类型，
说明原因并确认新的目标基线，重置为 `rc.0`。

从 RC 正式发布时，若数值基线已是相对上一正式版、按所选类型计算的目标，
只去掉后缀，例如 `3.0.2-rc.4` → `3.0.2`，不要再次递增 PATCH。
否则从上一相关正式版按所选类型计算目标；无正式发布记录且未指定目标时，
以当前数值部分按表中规则递增。明确要求发布当前 RC 则只去掉后缀。
不使用 `+build` 代替版本递增，因为 SemVer 排序不考虑构建元数据。

## 提交与发布

1. 确定类型和最终版本后更新 `VERSION`，与本次改动放在同一个提交中。
   同一次提交准备只递增一次；工作区已有相对 HEAD 的正确版本更新时复用。
   不覆盖与本次任务无关的用户改动。
2. 验证格式、版本顺序、暂存区差异和相关功能，确认暂存的 `VERSION`
   与父提交不同。提交说明写明更新类型、最终版本和兼容性影响。
   用户要求提交或发布时创建提交；仅要求编辑文件时不自动提交。
3. patch/minor/major 正式发布在包含最终版本的提交上创建附注标签 `vX.Y.Z`，
   例如 `3.0.1` 对应 `v3.0.1`。创建前确认标签不存在且提交中的 `VERSION`
   完全匹配；绝不移动或覆盖已有标签。若已存在并指向同一版本的目标提交，
   仅核验并报告，不重复创建。
4. 内部 `-rc.N` 提交不创建正式发布标签。完成后核验提交、标签指向和工作区状态，
   报告版本、提交哈希及标签。发布请求包含本地发布提交和标签；推送远端、
   创建 GitHub Release 或上传构建产物须有对应授权。
